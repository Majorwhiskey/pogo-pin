# 12. Testing strategy

| Layer | What it covers | Tooling |
|---|---|---|
| Unit | Log parsers, panic block parser, regex matching, durations, config merge, INA226 conversion | `cargo test` |
| Mock transport | Capture engine with scripted byte streams: partial lines, CRLF, lone CR, ANSI codes, garbage bytes, mid-line deadline | `MockTransport` |
| Record/replay | Real sessions recorded with `--record`, replayed in CI | `tests/fixtures/*.jsonl`, `ReplayTransport` |
| Snapshot | JSON outputs, human output, `--help` texts, schemas | `insta` |
| CLI integration | Exit codes, stdout/stderr separation, format flags | `assert_cmd`, `predicates` |
| Property | COBS/postcard round-trips, line splitter under arbitrary chunking | `proptest` |
| Hardware-in-the-loop | Real flash, capture, reset, panic, `info`, `doctor --deep` | `crates/pogo-cli/tests/hil.rs`, opt-in |

**Fixture coverage required by Phase 1:** clean boot with `READY`, timeout with no output, Rust panic with backtrace, ESP-IDF Guru Meditation with `Backtrace:` line, boot loop, brownout, device disconnect mid-capture.

**Recording format** (`--record`, `tests/fixtures/*.jsonl`): one JSON object per line. The first line is a header; the rest are events in time order, with `t_ms` counted from the start of the recording. Byte chunks carry `text` when they are valid UTF-8 and lowercase `hex` otherwise, so fixtures can be read and edited by hand.

```jsonl
{"type":"header","format":1,"pogo_version":"0.1.0","port":"/dev/cu.usbmodem1101","baud":115200}
{"type":"dtr","t_ms":0,"asserted":false}
{"type":"rx","t_ms":12,"text":"ESP-ROM:esp32c3-api1-20210207\r\n"}
{"type":"rx","t_ms":13,"hex":"ff00"}
{"type":"tx","t_ms":900,"text":"ping\n"}
{"type":"disconnect","t_ms":1500}
```

Other event types are `rts` and `baud`. `ReplayTransport` delivers `rx` chunks in order as fast as they are read (timestamps are not replayed, so tests run instantly), ignores writes and control-line changes, and fails with `DEVICE_IO` at a `disconnect`. A recording without a `disconnect` behaves like a connected, silent device once its data runs out. Timing-sensitive tests (settle windows, mid-line deadlines) use `MockTransport` with explicit delays instead.

**Replaying through the CLI:** with `POGO_REPLAY=<file>` set, `serial capture`, `serial send`, and `run --no-flash` read that recording instead of resolving and opening a device (`data.device.port` becomes `replay:<file>`), and the probe commands read it as the probe's side (see below). Flashing and `info` refuse to run on a replay. It is a test hook for exit-code and output tests, not a user feature. `tests/fixtures/synthetic/` holds hand-written sessions covering the Phase 1 fixture list; most model typical ESP32-C3 output, and `esp32_*`, `task_watchdog`, and `stack_overflow` model classic ESP32 (Xtensa) ESP-IDF faults (`abort()`, `LoadProhibited`, task watchdog, stack overflow); `tests/fixtures/real/` holds sessions recorded with `--record` on an ESP32-WROOM-32 (a devkit boot, and the test firmware reaching `READY` and panicking).

**Probe sessions:** `probe_*.jsonl` fixtures in `tests/fixtures/synthetic/` script the probe's side of a session (a `Hello`, then one response per request, as hex frames). `POGO_REPLAY` stands in for the probe in `probe`, `gpio`, and `i2c` commands just as it does for a board. The files are generated by pogo-core's `probe_fixtures_are_current` and `probe_power_fixtures_are_current` tests, which fails if they drift from the protocol; `POGO_UPDATE_FIXTURES=1 cargo test -p pogo-core probe_fixtures` rewrites them. Core tests also script the probe with `MockTransport` to check the exact requests each command sends.

**Test-target firmware** (`firmware/test-target/`, esp-hal) prints `READY` after init and accepts line commands over serial:

| Command | Behavior |
|---|---|
| `ping` | Replies `pong` |
| `panic` | Triggers an `unwrap()` on `None` at a known source line |
| `reboot` | Software reset |
| `busy <ms>` | Busy-loops (power tests) |
| `sleep <ms>` | Light sleep (power tests) |
| `gpio <n> <0\|1>` | Sets a target GPIO |

```console
cargo test --workspace                       # everything that doesn't need hardware
cargo insta review                           # review snapshot changes
POGO_HIL=1 cargo test -p pogo-cli --test hil -- --test-threads=1
```

HIL tests are skipped unless `POGO_HIL=1` is set, and they always run single-threaded. They live in `crates/pogo-cli/tests/hil.rs` and need one ESP32 connected (or `POGO_HIL_DEVICE=<port or USB serial>` to pick one of several) and the test firmware built (`cargo build --release` in `firmware/test-target`); with `POGO_HIL=1` and no firmware they fail with that instruction. Each test first makes sure the board is at `READY`, flashing the firmware if needed, so they do not depend on order. Covered: `run` flashes and reaches `READY` with one boot; `ping`/`pong`; the planted panic is reported at `src/main.rs:77` and symbolized to `trigger_panic`; `reset --mode bootloader` stops the app and `reset` restarts it; opening the port never resets the board; `info` and `doctor --deep`. They take about 30 s on an ESP32-WROOM-32 devkit.
